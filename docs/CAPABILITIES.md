# مهارت‌ها، ایجنت‌ها و ابزارهای The Last Civilization

## ۱. ابزارهای در دسترس

| ابزار یا سطح | کاربرد در بازی | بررسی این نوبت |
| --- | --- | --- |
| PowerShell، Git و `rg` | بررسی سورس، اجرای موتور و آزمون‌ها، بررسی diff و نگهداری تاریخچه | Git و `rg` محلی پیدا شدند و اجرا شدند. |
| Python و Node.js همراه Codex | فهرست‌برداری مهارت‌ها، ساخت ابزار کمکی کوتاه و ثبت شواهد اجرا | Python برای ممیزی این بسته اجرا شد. پروژه بازی بر GDScript پیشنهاد شده است. |
| FFmpeg و نمایش تصویر | استخراج فریم مرجع و مقایسه قاب‌ها. تصویر اجرای خود بازی برای شواهد QA | FFmpeg محلی برای بررسی فایل مرجع استفاده شد. |
| Node REPL، مرور وب و Computer Use | ابزار کمکی، مستندات رسمی، بررسی پنجره بازی در Windows و ثبت تصویر | Node REPL در تنظیمات و ابزارهای جلسه وجود دارد. Computer Use برای زمانی مفید است که بازی اجرا شود. |
| ImageGen و ابزارهای Adobe یا Canva | اتود هنری یا آیکن اختصاصی در صورت نیاز | ابزارها در جلسه دیده می‌شوند. تولید دارایی سه‌بعدی مستقل به ابزار ساخت سه‌بعدی نیاز دارد. |
| Visualize، PDF و Documents | نمودار اقتصاد، بررسی فایل مرجع یا بسته ارائه در صورت نیاز | در جلسه یا کش محلی دیده شدند. اسناد مرحله‌ای مستقیماً Markdown هستند. |
| Codex Desktop و همکاری چندایجنتی | فضای کاری، بررسی تغییر و امکان بازبینی مستقل در صورت نیاز | بازبینی این نوبت را ایجنت اصلی انجام داد. تعریف ایجنت سفارشی پروژه یا ایجنت ECC در مسیرها و تنظیمات بررسی‌شده پیدا نشد. |
| `graphify` | نقشه وابستگی‌های طراحی، اثر تغییر بر فایل‌ها و پیدا کردن مسیر بین تصمیم و آزمون | مهارت و CLI نسخه ۰٫۹٫۱۱۵ در پوشه مستقل بازی شناسایی شدند. [گردش‌کار و نتیجه اجرای Graphify](GRAPHIFY.md) |

پوشه‌ها و ثبت‌های محلی مهارت‌ها خوانده شدند. مشخصات و دامنه تمام فایل‌های پیدا شده برای فهرست‌برداری استخراج شد و مهارت‌های نامزد از نظر کاربرد، الزامات ابزار و تناسب با Codex بررسی شدند. کش افزونه با قابلیت فعال جلسه فرق دارد. [نمایه کامل فایل‌ها و شمارش](SKILL-INVENTORY.md)

## ۲. مهارت‌های ECC با کاربرد مستقیم

| مهارت | کاربرد مشخص | زمان استفاده |
| --- | --- | --- |

| `intent-driven-development`، `product-capability`، `product-lens` | محدود کردن نسخه اول به چند تصمیم قابل‌بازی و تعریف نتیجه قابل مشاهده هر گام | پیش از گام‌های ۱ تا ۵، وقتی دامنه نیاز به اصلاح دارد |
| `agentic-engineering`، `coding-standards`، `error-handling` | شکستن کار به تغییرهای کوچک، روشن نگه داشتن هسته اقتصاد و کنترل وضعیت‌های ناقص ساخت و ذخیره | گام‌های ۱ تا ۵ |
| `change-impact`، `codebase-onboarding` | دنبال‌کردن اثر تغییر از داده و شبیه‌سازی تا جهان، ذخیره و HUD. اگر مخزن سورس داشته باشد، پیدا کردن مسیرهای اصلی اجرا | بررسی مخزن مقصد و تغییرهای مشترک |
| `context-and-decisions`، `architecture-decision-records`، `docs-governance` | نوشتن تصمیم ساده درباره موتور، ساعت اقتصاد و ذخیره. نگهداری یک سند Markdown زنده برای هر گام | گام‌های ۱ تا ۵ |
| `git-workflow`، `conventional-commit-review` | شاخه کوچک، commit خوانا و بررسی محتوای diff قبل از ارسال | هر گام پس از اتصال مخزن |
| `github-ops`، `project-flow-ops`، `issue-review` | نگهداری PR و وضعیت آزمون، پیگیری خطاها و تحویل نسخه در GitHub | پس از اتصال. بخش CLI مهارت `github-ops` به `gh` نیاز دارد. |
| `tdd-workflow`، `verification-loop`، `test-collaboration`، `module-regression` | سناریوی قابل بازتولید برای اقتصاد، ساخت و آفلاین. اجرای Godot، تست مرتبط، کنترل دستی و ثبت شواهد | گام‌های ۱ تا ۵. دستورهای نمونه وب و Python مهارت با فرمان‌های Godot جایگزین می‌شوند. |
| `click-path-audit`، `accessibility`، `i18n-sync` | دنبال‌کردن ورودی تا نتیجه واقعی، کنترل متن و خوانایی فارسی، اندازه هدف‌های لمس و سازگاری HUD | گام‌های ۲ و ۵. `click-path-audit` یک مهارت مکمل با منشأ community است. |
| `terminal-ops`، `agent-self-evaluation` | ثبت خروجی واقعی اجرا و مرور نهایی تحویل در برابر معیار قبولی | پایان هر گام |

## ۳. مهارت‌ها و ابزارهای مکمل

| حوزه | مهارت‌های قابل استفاده | انتخاب عملی |
| --- | --- | --- |
| مرجع هنری | `taste-distillation`، `taste-application`، `video-editing`، `imagegen` | ویژگی‌های قابل تکرار مرجع مانند زاویه، رنگ و شکل رشد را استخراج می‌کنیم. ImageGen می‌تواند برای اتود و آیکن استفاده شود. |
| صحنه و انیمیشن | `blender-motion-state-inspection`، `animation-vocabulary`، `review-animations`، `animation-performance` | در صورت ورود مدل یا انیمیشن بیرونی، خوانایی حرکت و هزینه صحنه بررسی می‌شود. آغاز پروژه با هندسه ساده داخل Godot ممکن است. |
| تجربه کاربر و لمس | `break-ui`، `gestures`، `design-system`، `emil-design-eng`، `make-interfaces-feel-better` | اصول تعامل قابل استفاده‌اند. اجرای خود عناصر و gesture برای Godot از API موتور گرفته می‌شود. |
| تست تصویری و بنچمارک | `computer-use`، `ui-demo`، `windows-desktop-e2e`، `benchmark`، `benchmark-optimization-loop` | تست منطق با Godot headless و تست تصویری با اجرای واقعی. UIA فقط در صورت در دسترس بودن کنترل‌های Godot در درخت دسترس‌پذیری کاربرد دارد. برای نرخ فریم از Profiler موتور استفاده می‌کنیم. |
| نگهداری پس از شروع | `inherit-legacy-style`، `production-audit`، `quality-nonconformance`، `safety-guard`، `security-review` | اگر کد موجود باشد سبک آن حفظ می‌شود. این مهارت‌ها هنگام مشاهده نقص مشخص، بررسی بسته نهایی یا مرور فایل‌های حساس به کار می‌آیند. |
| تحویل و گزارش | `article-writing`، `visualize`، `code-tour`، `growth-log`، `brownfield-retrospective` | برای گزارش طولانی، نمودار تصمیم یا مرور بعد از تحویل مفیدند. سند کوتاه هر گام مرجع اصلی است. |

## ۴. شکاف‌های محیط و مسیر تکمیل

| شکاف | مسیر مناسب |
| --- | --- |
| مهارت اختصاصی Godot یا GDScript در فهرست پیدا نشد | از مستندات رسمی Godot برای موتور و از ECC برای طراحی، کیفیت کد، آزمون و تحویل استفاده می‌کنیم. `documentation-lookup` به Context7 متکی است و Context7 در ابزارهای فعال پیدا نشد. مرور وب به مستند رسمی دسترسی دارد. [مرجع Godot](https://docs.godotengine.org/en/stable/) |
| Godot، ابزار خروجی Android و CLI گیت‌هاب در مسیرهای معمول پیدا نشدند | در آغاز گام مرتبط، موتور پایدار مشخص و اجرای واقعی آن بررسی شود. اگر دسترسی GitHub از طریق Git موجود کافی بود، نصب CLI برای کار پایه ضروری نیست. SDK و دستگاه یا محیط آزمون Android هنگام رسیدن به تحویل Android باید تأیید شوند. [خروجی Android در Godot](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_android.html) |
| Playwright، مرورگر و ابزارهای وب | `e2e-testing`، `browser-qa`، `mobile-native`، `impeccable` و `design-taste-frontend` برای نرم‌افزار وب مناسب‌اند. در بازی بومی فقط اصول قابل انتقال آن‌ها به کار می‌آیند. |
| بعضی مهارت‌های ECC به قابلیت‌های Claude متکی‌اند | `delivery-gate`، `hookify-rules`، `gateguard` و بخش‌هایی از `orch-*` نیاز به بررسی سازگاری دارند. برای پنج گام، ثبت آزمون و PR شواهد کافی می‌دهد و فعلاً قلاب تازه لازم نیست. |
| افزونه GitHub پیدا شد و نصب نیست | پس از تعیین مخزن، دسترسی به همان مخزن با Git یا افزونه بررسی می‌شود. عملیات GitHub، ساخت مخزن و نصب افزونه در این نوبت انجام نشد. |

### ایجنت‌ها و نقش‌ها

| نقش | وضعیت | مسئولیت قابل تفکیک |
| --- | --- | --- |
| ایجنت اصلی Codex | فعال | پیش‌بردن گام با کاربر، تغییر کد، اجرای آزمون و مستندسازی |
| بازبین اقتصاد و ذخیره | نقش پیشنهادی برای بازبینی مستقل | تطبیق فرمول‌ها، هزینه‌های یک‌باره، آفلاین و ذخیره نیمه‌کاره |
| بازبین UX و پلی‌تست | نقش پیشنهادی برای بازبینی مستقل | اجرای واقعی مسیر کاربر، کنترل دوربین، HUD فارسی و لمس |
| بازبین تحویل GitHub | نقش پیشنهادی برای بازبینی مستقل | diff، تست‌های PR، اقلام نسخه و مسیر دریافت فایل اجرایی |

`team-builder`، `team-agent-orchestration`، `dev-team` و `council` گردش‌کار تعریف نقش یا بازبینی‌اند. وجود فایل این مهارت‌ها به معنی نصب یا اجرای ایجنت جدا نیست. برای این بازی ساده، ایجنت اصلی می‌تواند هر پنج گام را پیش ببرد. در صورت نیاز به بازبینی مستقل، نقش و خروجی آن هنگام شروع همان بازبینی مشخص می‌شود.

## ۵. اولویت اجرای بررسی‌ها

1. مشخص کردن مخزن مستقل و بررسی تاریخچه و سورس واقعی آن پس از دریافت نشانی.
2. تثبیت دامنه کوچک پنج گام، نقطه شروع تولید، رفتار آفلاین و معیار خروجی هر پلتفرم.
3. پیدا کردن یا آماده‌کردن Godot و ثبت نسخه دقیق پس از آغاز توسعه.
4. ساخت هر گام، اجرای بازی، ثبت نتیجه آزمون در سند همان گام و بررسی تغییر روی GitHub.
